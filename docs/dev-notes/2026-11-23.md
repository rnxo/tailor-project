# React Providerパターン

アプリの外部データのフェッチ最適化のために**Tanstack Query**を追加して移行作業をしていると、`ClientQueryProvider`というコンテキストを提供するためのコンポーネントを見た。
そのコンポーネントが、propsのバケツリレーをしないための**React**のデザインパターンの一種というのは知っていたけど詳しいことは理解していないと思ったのでこれを機に知ろうということでこの開発ノートを書こうと思った

## Provider Context パターンとは

主にpropsのバケツリレーなしでpropsを子コンポーネントに渡せることができる**React**のデザインパターンのひとつである。

簡単なコード例

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Page />
    </ThemeContext.Provider>
  );
}
```

`React.createContext`によってContextを作成し、`Context.Provider`によってアプリのコンポーネントを包むことでReactのコンポーネントツリーのどの階層からもpropsを使える。

## ユーズケースについて

参照: https://zenn.dev/fitness_densuke/articles/2026-01-02-react-provider-pattern

### 適用すべきケース

1. テーマ、認証、言語などの変更頻度が少ないグロバールステート
2. 3階層以上のpropsバケツリレーが発生しているとき
3. 複数の離れたコンポーネントが同じデータを必要としているとき

### 適用をさけるべきケース

1. 頻繁に変更されるステート
2. 単一コンポーネントでしか使わないローカルステート
3. サーバーなどの外部からのデータフェッチ

> 3.外部データのデータフェッチについて補足
> Tanstack Queryはまさにデータフェッチをしているのにも関わらず、Providerパターンをっ使用している。これはアンチパターンかのように思うけど実際にはProviderのvalueに渡している値が違う

アンチパターンとなるコード

```jsx
const UserContext = createContext(null);

function UserProvider({ children }) {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  useEffect(() => { 
	fetch('/api/users')
	  .then(r => r.json())
	  .then(setUsers)
	  .finally(() => setLoading(false)); 
  }, []);
  
  const value = useMemo(() => ({ users, loading }), [users, loading]);
  return (
	<UserContext.Provider value={value}>
	 {children}
	</UserContext.Provider>
   );
}

```


一方、Tanstack Queryのコード

```jsx
const queryClient = new QueryClient();

<QueryClientProvider client={queryClient}>
  <App />
</QueryClientProvider>
```


アンチパターンのコードでは、`users`と`loading`をまとめたオブジェクトを`useMemo`でメモ化し、Providerの`value`に渡している。`useMemo`によって無駄な作り直しは防げるが、データが更新されれば依存配列の`[users, loading]`が変わるので、新しいオブジェクトが作られる。Reactは`Object.is`で参照を比較して「値が変わった」と判断し、`UserContext`を読んでいるすべてのコンポーネントを再レンダリングされる。

一方、TanStack Queryでは、Contextに渡すのはキャッシュを持つ`QueryClient`のインスタンスで、アプリが動いている間その参照は変わらない。キャッシュの中身が更新されても`queryClient`自体は同じオブジェクトのままなので、`Object.is`は変更なしと判断し、Contextが原因の再レンダリングは起きない。データの変化は、Contextではなく`useQuery`による購読を通して伝わる。そのため、変わったクエリを使っているコンポーネントだけが再レンダリングされる。

これらのことから言えることとしては、**Providerパターン**を使用していいのは`Object.is`によって参照比較をするときに「値が変わっていない」と判断されない`Context`を`Provider`の`value`にしているとき。
